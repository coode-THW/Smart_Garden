## 一、背景与现状

| 项目 | 现状 |
|------|------|
| 模型 | YOLOv11n 分类，9 类花卉，输入 `224×224` FP32，输出 `[1,9]` 已内嵌 softmax |
| 产物 | `models/yolov11n-flower.onnx`（FP16，约 5.9MB）+ APP 内副本 `SmartGarden/assets/` |
| 推理链路 | 预处理 → ONNX Runtime（iOS CoreML / Android XNNPACK / 兜底 CPU）→ 多维置信度决策 |
| 运行目标 | **算力有限的边缘设备与手机上，以精度优先的方式运行本项目** |
| 已有工程配套 | `ModelUpdateService`（远程版本检查 + INT8 量化位支持）、`YoloService`（加载/基准测试）、`ImagePreprocessor`、`RecognitionOrchestrator`、`useRecognition` 状态机 |

**本次优化的三个方向与任务模式：**

1. **本地部署（唐宏苇）** — 探索在算力有限的边缘设备和手机上的本地部署方案，精度优先运行。
2. **训练与数据（余浩）** — **周循环模式**：每周训练更多植物品种，训练结果直接决定下一轮数据采集任务。
3. **流程与状态机（孙睿智）** — **持续优化模式**：不断优化本项目整体的进程设计，**在保证精度的前提下优化延迟**。

## 二、人员角色与职责

| 成员 | 原角色 | **新分工（v2.1）** | 任务模式 | 目标 |
|------|--------|-------------------|----------|------|
| **唐宏苇** | 前端/UI/集成 | **本地部署探索** | 方案探索 + 基线维护 | 算力有限的边缘设备与手机上**精度优先**本地运行 |
| **余浩** | AI 模型/ONNX/LLM | **模型训练 + 数据采集统筹** | **周循环**（训练 → 评测 → 定数采） | 每周训练更多植物，按训练结果调配数采，持续提高准确性 |
| **孙睿智** | 知识库/数据/测试 | **流程与状态机设计** | **持续迭代**（度量 → 优化 → 精度回归） | 不断优化整体进程设计，**保证精度的前提下优化延迟** |

```
     唐宏苇 (本地部署)          余浩 (训练/数采·周循环)      孙睿智 (流程/状态机·持续)
     ┌────────────────┐       ┌────────────────┐       ┌────────────────┐
     │ 端侧推理后端选型  │ ←模型─ │ 每周训练更多品种  │       │ 进程设计持续优化  │
     │ 精度优先量化策略  │       │ 训练结果→数采任务 │       │ 延迟优化(保精度) │
     │ 真机适配/基线    │ ─错分─→│ 弱类补采→再训练   │ ←链路─ │ 状态机/编排/并发  │
     └────────────────┘       └────────────────┘       └────────────────┘
              │                        │                        │
              └────────── 端到端精度·延迟联调 ─────────────────────┘
```

**协作原则：**

- **精度优先是共同底线**：部署侧（唐）不得以牺牲精度换体积/速度；训练侧（余）产出的模型是精度的源头；流程侧（孙）优化延迟不得改变识别决策语义。
- **训练结果驱动数采**：每周训练评测出的弱类/错分/缺场景，直接转化为下一周数据采集任务单（余浩统筹），部署与流程侧的异常样本同步并入。
- **改动同步**：涉及模型输入输出约定、类别顺序、状态机事件定义的变更，三方在合入前互相确认。

## 三、优化工作分解（WBS）

### 3.1 本地部署探索（主责：唐宏苇）

| 编号 | 任务 | 产出 |
|------|------|------|
| P1 | 端侧推理后端选型与调研（XNNPACK / CoreML / CPU / NPU delegate） | 后端选型对比报告 |
| P2 | 精度优先的量化与部署策略（FP16 优先；INT8 仅在精度不降时采用） | 部署精度-体积取舍报告 |
| P3 | 模型加载链路优化（assets → 文档目录缓存、冷启动预加载） | 加载耗时与内存占用基线 |
| P4 | 多机型真机适配（含低算力设备）与端到端性能基线 | 真机性能基线表 |
| P5 | 边缘设备（开发板/树莓派级）本地运行可行性验证 | 边缘设备运行验证记录 |
| P6 | 部署侧错分/精度异常样本收集，汇入每周数采任务单 | 异常样本清单（交余浩） |
| P7 | 承接每周新模型的部署侧验证（加载/推理/精度不降） | 周模型部署验证记录 |

### 3.2 模型训练与数据采集统筹（主责：余浩）— 周循环模式

**任务模式：以「周」为单位滚动推进。每周训练更多植物品种；每轮训练评测结束后，根据结果适当安排下一轮数据采集任务，形成「训练 → 评测 → 数采 → 再训练」闭环。**

**每周固定循环：**

| 周内阶段 | 任务 | 产出 |
|----------|------|------|
| ① 训练 | **训练更多植物品种**：类别扩充 + 新样本训练/微调 | 当周模型 + 品种清单 |
| ② 评测 | 逐类准确率 / 混淆矩阵 / 错分样本统计 | 周训练报告 |
| ③ 数采决策 | **根据训练结果安排数据采集任务**：弱类补样本、缺场景（光照/角度/背景）补场景、错分类对重点采集 | 周数据采集任务单 |
| ④ 数采回收 | 执行采集、标注、清洗，数据入下周训练集 | 新增数据入库 |

**支撑任务：**

| 编号 | 任务 | 产出 |
|------|------|------|
| T1 | 训练环境与脚本恢复（git 历史 `34da349` 的 `train.py` / `export_onnx.py` 等） | 可复现训练环境（一次性） |
| T2 | 数采方案总纲与优先级基线（品种扩展路线、场景覆盖策略） | 数采方案文档（随周报滚动更新） |
| T3 | 数据规范（标注格式、难样本定义、清洗规则） | 数据规范文档（一次性） |
| T4 | 错分归因：汇总部署侧 P6 + 流程侧 F5 样本，计入周数采任务单 | 归因记录（每周） |
| T5 | 类别扩充三方复核（模型输出 ↔ `class_order.json` ↔ `flowerClasses.ts` ↔ 知识库映射） | 类别对齐确认单（每次扩类必做） |
| T6 | 周度汇总：品种增长数、准确率变化、数采完成情况 | 周训练与数采简报 |

> **扩类注意**：当前模型输出为 `[1,9]`。每扩充一类，输出维度、`class_order.json`、`flowerClasses.ts`、知识库映射四处同步改，改完必跑类别一致性用例。

### 3.3 流程与状态机设计（主责：孙睿智）— 持续优化模式

**任务模式：持续迭代，不设一次性终点。围绕「保证精度的前提下优化延迟」，按「度量 → 定位 → 优化 → 精度回归」循环推进，每轮优化都以精度不降为合入前提。**

**每轮优化循环：**

| 阶段 | 任务 | 产出 |
|------|------|------|
| ① 度量 | 端到端延迟埋点与分解（启动预加载 / 预处理 / 推理 / 决策 / LLM / 渲染） | 延迟分解数据 |
| ② 定位 | 找瓶颈：无效等待、可并行的串行段、重复计算、超时/重试过长 | 瓶颈清单 |
| ③ 优化 | 改进程设计：状态机转移精简、编排器并发/缓存/超时策略、模块协作逻辑 | 优化落地 |
| ④ 精度回归 | **精度不降验证**：决策语义与识别结果一致性对比 + 全量 Jest | 精度回归记录（不通过则回滚） |

**支撑任务：**

| 编号 | 任务 | 产出 |
|------|------|------|
| F1 | 延迟度量口径与埋点建设（各阶段可量化） | 延迟度量方案 |
| F2 | `useRecognition` 状态机持续优化（idle/camera/inferring/result/error 转移合理性） | 状态机设计说明（滚动更新） |
| F3 | `RecognitionOrchestrator` 决策流程持续优化（超时/重试/缓存/并发） | 编排器优化记录 |
| F4 | 精度回归基线建设（结果一致性对比方法、回归用例集） | 精度回归基线 |
| F5 | 流程运行异常（卡顿、误转移、重复识别）记录，反馈数采与部署 | 流程异常清单 |
| F6 | 回归用例随每轮优化补充，保持 Jest 全绿 | 测试用例补充 |

> **延迟优化的边界**：可以改等待、改并发、改缓存、改超时；**不得**以「降延迟」为由调整置信度阈值或 LLM 兜底策略来换取更快的拒绝路径——那属于换精度，不是优化延迟。

## 六、风险与注意事项

1. **延迟优化不能吃精度** — 流程侧每轮优化以「精度回归通过」为合入门槛；降阈值、砍 LLM 兜底、跳过预处理检查等提速手段一律不算优化，走三方确认另行决策。
2. **扩类是红线操作** — 每新增植物类别，四处（模型输出维度、`class_order.json`、`flowerClasses.ts`、知识库映射）同步改，改完必跑类别一致性用例；识别「张冠李戴」比识别率低 1 个点严重得多。
3. **ONNX 已内嵌 softmax** — 任何后处理不要再做一次 softmax（历史 double-softmax bug 曾让置信度从 90% 掉到 40%）。
4. **x86 模拟器 FP16 精度问题** — 部署与延迟结论以真机为准；模拟器异常先对照已知问题清单再判断。
5. **精度优先 ≠ 拒绝一切量化** — INT8/FP16 可以做，但必须先有量化前后精度对比数据；精度下降则不采用，体积问题另行解决。
6. **数采任务单要「适当」** — 按训练结果定向补采（弱类、缺场景、错分类对），避免漫无目的堆数据；同时注意隐私约定（纠错仅存 `imageHash`，不上传原图）。
7. **训练脚本恢复注意范围** — 只从 `34da349` 取脚本，不覆盖现有模型产物。
8. **`.env` 与 API Key** — 训练/评测脚本若涉及 LLM 校验，`QWEN_API_KEY` / `DOUBAO_API_KEY` 绝不入库。
9. **已知坑在流程改造中保持警惕** — `useFocusEffect` 失焦重置、超时定时器 `finally { clearTimeout }`、嵌套 ScrollView 等约定，改进程设计时避免改出回归。
